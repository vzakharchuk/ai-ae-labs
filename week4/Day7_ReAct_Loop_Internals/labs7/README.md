## Що зробив

`react.go` — цикл Thought → Action → Observation руками, без ADK. Звичайний `for`, на
кожній ітерації перевірка `MaxIterations`, виклики інструментів один за одним (не паралельно),
результати складаю назад в history по `CallID`. Якщо ліміт вичерпано — повертаю помилку з
`ErrMaxIterations`, не просто обрізаю мовчки.

`graph.go` — та сама штука, тільки крок це `NewDynamicNode` + `RunNode`. Тут була заморочка:
`RunNode` віддає назовні тільки `StepResult` (те, що йде в event log), а мені в циклі потрібен
повний `Step` з усіма викликами й текстом відповіді. Зробив через closure-змінну — крок кладе
туди весь `Step`, цикл одразу після `RunNode` її читає. Працює, бо `RunNode` блокує, доки дитина
не закінчить, тож ніхто інший в цей момент туди не долізе.

Момент, який не став приховувати: `history` і цю closure-змінну тримаю просто в пам'яті навколо
агента, не в `ctx.State()`. Для одного запуску з консолі це норм — агент створюється раз на
процес. Але якщо той самий агент піде у веб і обслуговуватиме кілька розмов одночасно — вони
потовчуться в одних і тих самих змінних. Знаю про це, не чіпав, бо виходить за межі завдання.

Ще додав тест, якого в шаблоні не було: на graph-версію з лімітом ітерацій
(`TestGraphStopsAtIterationLimit`). У main_test.go стояв тест тільки на ручну версію, а в чеклисті
прямо написано, що графова теж має це перевіряти. Узяв той самий planner, що ніколи не завершує,
прогнав через `NewGraphAgent`, перевірив `errors.Is(err, ErrMaxIterations)` — проходить, помилка
не губиться по дорозі через обидва шари обгортки.

## Рушій / я

| Рушій бере на себе | Моя відповідальність |
|---|---|
| Event log на кожен крок | Коли зупинятись і бюджет (ітерації, токени, час) |
| Типізований вхід/вихід вузла (`RunNode[StepResult]`) | Зв'язати виклики з результатами за `CallID` |
| Retry/timeout на рівні вузла | Що агенту взагалі дозволено викликати |
| Валідація схеми інструмента | Ідемпотентність побічних ефектів |
| Помилка доходить нагору сама (через `%w`) | Де тримати стан циклу — я вибрав closure, і це має свою ціну |
| `NewDynamicNode` як один вузол графа | Паралелізм усередині кроку — у мене все послідовно |

## Коли писати руками, коли в графі

Руками — коли цикл сам по собі, його ніхто більше не бачить. Швидше написати, простіше
прочитати, усе в одній функції.

У графі — коли крок циклу має жити поруч з іншими вузлами того самого workflow і ділити з
ними одні й ті самі політики — event log, retry, валідацію. Як у ДЗ 6. Плата за це — зайвий
рівень непрямості (та сама closure) і що стан між кроками не живе сам собою, треба про нього
подумати окремо.
